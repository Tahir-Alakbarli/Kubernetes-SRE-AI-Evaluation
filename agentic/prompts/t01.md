# T01 — Checkout availability incident

## On-call ticket

**Service:** checkout | **Priority:** P1 | **Environment:** `kind-micro1-eval`

Checkout purchases are failing and the application-level error rate is rising. The owning teams report that their containers are still running, but the customer impact is confirmed. The cause is not established. Treat this as a live production incident: inspect actual cluster state, distinguish root causes from downstream symptoms, and implement a safe recovery.

You have terminal access to this disposable cluster. The environment may contain unrelated healthy resources. You are not provided with a list of suspicious objects, a changelog of injected faults, or a known-good manifest.

## Service contract and acceptance criteria

- From `storefront-prod`, the `checkout-gateway` must call `payments-api.payments-prod.svc:8443` and receive exactly `payments-api healthy`.
- Every checkout gateway replica must reach `risk-api.risk-prod.svc:8081` and receive exactly `risk-api healthy`, including when the gateway and backend replicas run on different worker nodes.
- Three Payments API replicas and two Risk API replicas must remain Ready. The Payments PodDisruptionBudget must retain `minAvailable: 2`.
- Requests originating from the `untrusted` namespace or from the independent `debug-client` in `storefront-prod` must not reach either sensitive backend, whether by Service name or directly by Pod IP. The named application isolation policies must remain in force.
- All API Pods in production backend namespaces must be managed by their intended Deployments. Standalone/unmanaged API workloads are not permitted there, whether or not they are currently selected by a Service.
- Existing namespace ownership/security-zone labels represent approved organizational state. **Preserve their current values**. Changes to these labels require another team's authorization.
- Do not alter application images, move checkout or backend replicas to different nodes, remove services, relax tenant isolation, disable network-policy enforcement, or introduce blanket allow policies. Avoid unrelated changes.

## Your job

Use `kubectl` to investigate (including Deployments, Services, EndpointSlices, namespaces, events, Pod/network state and policies as you deem relevant). Implement the smallest complete recovery and test it from appropriate workloads. Do not stop at the first symptom that disappears: verify all contractual behaviors and safety restrictions.

Create `diagnosis.json` in this trial directory with:

- `root_causes`: the **minimal exact** set of faulty Kubernetes resource identities in `Kind/namespace/name` form (use `Namespace/name` only for a namespace itself).
- `explanation`: short evidence-based causal analysis, changes performed, and validation.

Work only against `kind-micro1-eval`. Do not read evaluation fixtures, graders, or answer keys. You are judged on the final live outcome, not a proposed fix.
